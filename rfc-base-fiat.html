RFC-001: OCTA on Base + fiat on/off ramps

A concrete, buildable spec for bringing OCTA to Base and giving everyday users a way to buy in with a credit card — researched from public sources, with honest trade-offs and a phased plan the team can actually execute.

TL;DR

The proposal, in one paragraph.

OctaSpace should ship an official, verified OCTA token on Base (recommended: LayerZero OFT standard or a canonical lock-and-mint bridge the team controls), publish a canonical token-list JSON so wallets and dApps resolve the real contract, and add fiat on/off ramps in phases — starting with a self-serve ramp widget for USDC on Base (no team permission needed to prototype), then listing OCTA as a buyable asset with a ramp provider once the team completes KYB. The community can build the RFC, the demo widget, the Base SDK scaffold, and the scam-token warning list unilaterally; only the team can deploy the canonical contract, sign commercial ramp agreements, and handle licensing.

Status quo — what exists today

Researched 2026-09-27 from OctaSpace's blog, docs, X, GitHub org, and third-party trackers. Unverified items are labeled.

OCTA on Base

  • No official OCTA token exists on Base. No Base deployment is mentioned on the OctaSpace blog, docs, X posts, or GitHub org. The whitepaper describes two networks only: the PoW L1 (native OCTA) and the internal PoA L2 used for billing.
  • Official OCTA representations today: the native coin on the OctaSpace L1, and wOCTA (ERC-20) on Ethereum mainnet with a Uniswap V4 pool (per third-party listings).
  • The official SDKs (JS, Python, Go, Ruby) are pure REST API clients — zero EVM/Base references: no chain IDs, no bridge code.
  • What does exist on Base under the OCTA name: unofficial copycats (details in the warning section). Treat any "OCTA on Base" token you find today as guilty until proven innocent.

Fiat on/off ramp

  • No fiat on-ramp or off-ramp product exists, and none is announced. No Transak / MoonPay / Banxa integration appears in any official channel.
  • Zebec partnership (July 29, 2025) — the only official fiat-adjacent integration: Zebec integrated the OctaSpace chain into its Silver & Carbon Mastercard debit cards, letting holders load and spend OCTA at Mastercard merchants; a co-branded "Zebec Black x OCTA" card was described as in development. Scope note: this is spend-only — you cannot buy OCTA with fiat through it, and it is not a bank-withdrawal rail. Co-branded card status: re-checked 2026-09-29 — no public evidence it has shipped; every source found (including Zebec's own announcement) still lists it as \"in development\". The Silver & Carbon integration is the live spend path today.
  • Third-party only: Bitget lists OCTA and offers card/bank buys routed through Alchemy Pay, Banxa, Mercuryo, and Simplex — that is Bitget's gateway infrastructure, not OctaSpace's.
  • Platform deposits today: OctaSpace Cube accepts crypto deposits via Web3 wallets. No fiat rails.

Why Base, and why fiat ramps

🌉

Base is where retail on-ramps land

Coinbase's L2 is the default destination for first-time crypto buyers in the US. An official OCTA on Base puts the token one hop from every major fiat ramp and wallet, instead of requiring users to learn a new L1 first.

💳

Fiat is the #1 consumer friction

Today a new user must already own crypto to rent a GPU. A credit-card on-ramp turns "rent a 4090 for an evening" into a 2-minute signup flow — the single biggest unlock for consumer growth vs Vast.ai and Salad.

🧲

Liquidity follows the canonical token

Right now, Base DEX liquidity for "OCTA" is fragmented across scam copycats. One official, verified contract consolidates liquidity and gives aggregators something safe to route through.

🛡️

Delay has a scam cost

Every month without an official Base token, copycats fill the vacuum and real users get burned. Verified 2026-09-30: a token-info aggregator still labels one of the copycats (0xd2cedc7c…805) as OctaSpace's "official" contract — see the scam-token warning. Shipping the canonical contract is the consumer-protection move.

Part A — OCTA on Base: design options

Three viable architectures. Only the OctaSpace team can deploy the canonical contract — this section exists so the choice is informed, not improvised.

OptionHow it worksProsCons
A. Canonical lock-and-mint bridge Team deploys an ERC-20 on Base; native OCTA locks in a team-controlled vault, 1:1 mints on Base (and burns on return). Simple mental model; team keeps full custody control; no third-party protocol risk. Team operates bridge infra (relayer, monitoring, pause controls); bridge code must be audited; single-operator trust assumption.
B. LayerZero OFT OCTA deployed as an Omnichain Fungible Token; burns on source, mints on destination via LayerZero messaging. Battle-tested standard; no pooled liquidity to attack; easy future expansion to other chains; no custom bridge to operate. Depends on LayerZero infra; small per-message fees; team still deploys and owns the contracts.
C. Route via existing wOCTA (Ethereum) Bridge the existing Ethereum-mainnet wOCTA to Base with a standard ERC-20 bridge. Fastest path; reuses the audited wOCTA contract. Two-hop mental model (L1 → Ethereum → Base); Ethereum gas for the first hop; inherits wOCTA's existing trust assumptions.
Recommendation: Option B (LayerZero OFT), fallback A.

OFT removes the honeypot problem of a lock-and-mint vault and the team never has to operate relayer infrastructure. If the team prefers zero external dependencies, Option A is a fine, well-understood alternative — but it must ship with audited contracts, a pause mechanism, and published monitoring.

Canonical contract checklist (applies to any option)

  • Source code verified on BaseScan before any announcement.
  • Standard ERC-20 metadata (name, symbol, 18 decimals); ownership/roles documented.
  • Published in a canonical token-list JSON at a stable URL (see data/octa-tokenlist.json — community draft, to be superseded by the team's official list).
  • Announcement from official OctaSpace channels linking the contract — this is what makes it "official," not the code alone.
  • Seeded DEX liquidity on Base (team-seeded pool, disclosed amounts) so the first users aren't trading against copycats.

Part B — Fiat on/off ramp: provider comparison & phased plan

Reality check first: getting OCTA listed as a buyable asset on any ramp provider is a commercial agreement that only the OctaSpace team can sign (it requires their KYB/business verification). Everything below is designed around that constraint.

Ramp provider comparison

ProviderIntegrationNotes for OctaSpace
Transak Self-serve dashboard, sandbox keys, embeddable widget + API Fastest to prototype (sandbox needs no partnership). Listing OCTA as a direct-buy asset still needs a commercial agreement + KYB.
MoonPay Widget + API, sandbox environment Strong US card coverage. Same caveat: sandbox is self-serve, production asset listing is a partnership.
Coinbase Onramp API-first, USDC-centric Natural fit for a Base-first strategy (fiat → USDC on Base in one step). Asset support is Coinbase-gated.
Banxa Widget + API Already in Bitget's OCTA buy flow — familiarity upside, same partnership requirement for direct integration.

Phased plan

Phase 0 · community · no permission needed

This RFC + scam-token warning + token-list JSON

Establishes the design consensus and protects users today. Shipped with this page.

Phase 1 · community prototype · sandbox keys only

On-ramp widget demo: fiat → USDC on Base

A standalone demo page embedding a Transak/MoonPay staging widget showing the exact UX the team would adopt: card payment → USDC lands on Base. Clearly labeled demo, not production. Proves the flow end-to-end without any team account, and pairs with a DEX-swap step (USDC → OCTA via an aggregator quote) to complete the "buy OCTA with a card" story.

Shipped: sandbox on-ramp demo — fully simulated quotes (no staging keys needed), mock USDC → OCTA swap using the live OCTA price, and a mock confirmation receipt.

Phase 2 · OctaSpace team

Official Base token + canonical token list

Deploy the canonical contract (Part A), verify on BaseScan, publish the official token list, announce from official channels, seed DEX liquidity. This is the step that kills the copycats.

Phase 3 · OctaSpace team + commercial agreements

Production ramps: OCTA as a buyable/sellable asset

Team completes KYB with a chosen ramp provider, gets OCTA listed as a direct-buy asset, and embeds the production widget in Cube (buy) plus a sell widget or bank-withdrawal rail (off-ramp). Until then, the Zebec card remains the spend path and third-party exchanges remain the off-ramp.

What the community will NOT do:

Deploy anything that looks like official OCTA · operate custody or bridges with user funds · sign up for ramp-provider production accounts in OctaSpace's name · touch the team's private keys or billing infra. The line between "helpful prototype" and "impersonation" is bright, and we stay on the right side of it.

Part C — SDK support

What developers need to build on top of all this.

  • New viem-based helper package in the js-sdk style: Base mainnet (chain ID 8453) and Base Sepolia (84532) chain configs, ERC-20 helpers (balance, transfer, allowance, decimals).
  • Testnet-first: build and test against a throwaway ERC-20 on Base Sepolia — no official contract needed to start.
  • Token-list consumer: a tiny resolver that loads the canonical token-list JSON and returns the official contract address per chain — so dApps never hardcode (or trust) a copycat.
  • Demo dApp (Phase 1): "pay for GPU hours with OCTA on Base" — wallet-connect + mock invoice settled in the Sepolia test token. Proves the UX; the real version needs the official contract + billing API cooperation.
  • All of this can be developed unilaterally and offered to the team as PRs against their SDK repos.

Security & compliance notes

  • Impersonation risk is the #1 hazard. Any community token, widget, or page must be unmistakably labeled unofficial/demo. Nothing we ship may look like an official OctaSpace product.
  • Ramp providers handle KYC/AML — that's the point of using them instead of building money transmission in-house. The team never touches user fiat directly in this design.
  • Money-transmitter licensing stays with the licensed ramp provider; OctaSpace's KYB is a business-verification step, not a license application — but the team should confirm with counsel before signing.
  • Bridge custody (Option A): if the team runs lock-and-mint, the vault needs audited contracts, a pause mechanism, multisig control, and public monitoring. This is the strongest argument for Option B (OFT).
  • Phishing: the official announcement must come from official channels with a verified BaseScan link. The community will amplify only that link.
